## Running things

```bash
# tests (real MySQL, ~7 min)
docker compose -f docker-compose.yml -f docker-compose.test.yml run --rm tests

# replay a real day against the dispatcher's hand-entered log
docker compose -f docker-compose.yml -f docker-compose.test.yml run --rm replay
#   REPLAY_PHOTOS=1  also run vision (slow, costs API calls)
#   REPLAY_DRIVER="JOHN SHIM"  narrow to one driver
#   REPLAY_DEBUG=1   why each unmatched manual row was rejected
# legs stay in `replay_scratch` afterwards; the next run rebuilds it

# live parser checks (need GEMINI_API_KEY, not part of the suite)
tests/bench_live_parser.py  bench_live_shift_cases.py  bench_live_missed_messages.py
```

Docker is native `docker.io` inside WSL2 (systemd), **not** Docker Desktop.
MySQL cannot use a `/mnt/c` bind mount — InnoDB will not initialise on drvfs;
the test overlay uses a named volume.

## Architecture

`bot/` — `main.py` (startup, seeding, JobQueue), `config.py` (table names),
`schema_ddl.py` (**the only schema definition**), `ai_engine.py` (Gemini text +
vision, location cache), `handlers.py` (Telegram), `state_machine.py`
(`commit_trip_leg`, all cases), `routes.py`, `load_types.py`, `rm_manifest.py`,
`manifests.py`, `shifts.py`, `dwell.py`, `seed_network.py`.

`bot/data/` is operational data, edited not coded: `locations.csv`,
`docks.csv`, `drivers.csv`, `load_types.csv`, `location_distance.csv` (routes
are seeded from `routes.py`).

**There are TWO copies of every one of those CSVs** -- `bot/data/` and the
repo-root `data/` -- and both are tracked. **The code only ever reads
`bot/data/`** (`seed_network.DATA_DIR` and `load_types.CSV_PATH` are both
relative to `bot/`). Root `data/` also holds the Telegram export and the
dispatcher's workbook, which the replay needs and the bot does not. Edit
`bot/data/` or the change does nothing. This has already bitten once: see Open
items.

## Domain model

**Geography** is an I-75 corridor: Dalton north (E1, E2F, E2R, SDS, 210, 3551),
Adairsville middle (200F, 200R, 7634, 300), Cartersville south (100, 1380).
Truck repos are **200** and **SDS**. Client calls the plants Eagle 1/2/3; only
Eagle 2 has front/rear. `200F`/`200R` and `E2F`/`E2R` are **one site each**.

**Seven defined routes** (`routes.py`, seeded to DB):
R1 `200F→E2F/E2R→SDS→200F`, R2 `200F⇄SDS`, R3 `SDS⇄200F`, R4 `SDS⇄7634`,
R5 `E1⇄210`, R6 `3551⇄E1/E2F/E2R`, R7 `200F⇄7634`.

**A round** is one traversal of a route: leave an anchor, work the stops
belonging to a route anchored there, return. Anything off-route is a **spot
delivery** forming its own round.

**Load type** comes from the lane, on LOADED legs only (`load_types.csv`).
`200→E2` RM, `E2→200` RM Inbound, `SDS→200` FG STO, `200→SDS` Spot Delivery,
`E1⇄210` FG E1, `200⇄7634` FG ES, `SDS⇄7634` FG DS, `3551⇄E1/E2` RM 3551.
OQC/IQC Recall stay with the dispatcher's dropdown — indistinguishable from RM.

**Doors are numbered in bands, and the band is the meaning** (`docks.csv`).
At 200 the front building runs **3-21 FG inbound** and **22-45 RM inbound**
(worked by **Hanjin**, not us); the rear runs **47-66 RM outbound** and
**67-99 FG outbound** (the 200⇄7634 lane). Upper bounds are approximate and 46
belongs to nobody. So a driver naming only a door has named a building: "#3 to
#47" is 200F→200R. After a live unload on an inbound door, drivers stage the
empty on a **vacant RM outbound door** so the next RM round -- theirs or
another driver's -- can hook and go. Only the 200 site has bands recorded.

**Dwell** (arrival → next departure) is the metric that differentiates, not
ETA; every operator meets transit times. Thresholds 20/30/40 min, escalating
once per level.

## Critical constraints — DO NOT OVERWRITE

- **`bot/schema_ddl.py` is the only schema.** `init.sql`/`schema.sql` were
  deleted for drifting. Never add a second copy. Test fixtures seed via the
  production path for the same reason — three hand-written copies drifted.
- **Round grouping is NOT distance-based.** Tried and failed: `E1→210` is short,
  and 100/1380 are *nearer* to 200 (15.5/19.1 mi) than every routine stop (21+).
  Cycle detection also fails. A test pins this.
- **`python-telegram-bot` 20.8 (httpx~=0.26) and `google-genai` 2.x
  (httpx>=0.28.1) are incompatible.** google-genai pinned to 1.2.0. Upgrading
  it needs PTB 22.x first. `[job-queue]` extra is required for dwell alerts.
- **Model is `gemini-flash-lite-latest`.** Verify model ids against ListModels,
  never from memory (`gemini-3.5-flash-lite` is real but flakier: 3/5 vs 5/5).
- **Gemini calls must stay in an executor**; they block and retry ~15s.
  `PARSE_POOL_WORKERS=32` because the default is 8 on a t3.xlarge.
- **A parse failure must never return `NONE_WORK_RELATED`** — that silently
  discards the movement. Use `PARSE_FAILED`, which raises a card.
- **Movement always wins over a completion or a lunch report.** Real messages
  carry both ("7634 unloading finished Empty to 200R"). Choosing the completion
  loses the trip. Same for lunch.
- **Never merge expected and reported columns.** The dispatcher owns expected,
  the bot owns reported; an inferred time in a reported column becomes
  indistinguishable from an observation. Applies to shifts, arrivals, manifests.
- **A duplicate BOL is a driver error, never an override.** Record the movement,
  discard the stale paperwork, card for a repost.
- **Timestamps come from Telegram**, including `forward_origin` for forwards.
  Never `datetime.now()`.
- **Facility codes are never docks or trailers.** Guards exist in both places.
- **A drop at the facility a trip is still running to is that trip's ARRIVAL**,
  not a yard move. The parser cannot tell -- only the open leg knows the driver
  was on their way there. Guarded to drops with no position moved FROM and no
  second place named, so "door 7 to yard" and "200F to 200R" stay moves.
- **A leg's `trailer_number` is often inherited, not observed.** CASE 1 copies
  it from the driver's previous leg when the message names none, so it goes
  stale at the first trailer swap. Never treat it as evidence; a trailer named
  at a drop is first-hand and wins.
- **PACTRA means 200, not 7634** — SDS bought the site from Pactra and long
  serving drivers still use the old name. 7634's official name is EPC PACTRA,
  which makes the wrong answer look right.

## Done 2026-08-30 (uncommitted, working tree)

Four defects found by replaying 08/28 against the dispatcher's log, all fixed
with tests. `state_machine.py` CASE 3 is where most of it lives.

1. **A drop at the destination created a second leg.** "Pickup empty pactra to
   sds" 07:32, then "Drop empty trailer at sds yard D021 #25773" 08:09 -- the
   drop was filed as an SDS→SDS yard move and the real leg stayed open until
   the next departure closed it at 08:20. Now it completes the open leg with
   the drop's time, dock, DO# and trailer. Sokhwan Yun's three SDS runs now
   match the dispatcher's log exactly (arrival, trailer and DO# on all three).
2. **A load hooked with no destination vanished.** "Load trailer pickup sds
   dock28 #77209" -- the driver never said where it was going, so nothing was
   recorded and nothing was said. Now raises **MANUAL RECONCILE: Load Picked Up
   With No Destination**, from both the yard-move and the arrival paths, and
   still writes no leg (a leg to UNKNOWN enters a round and a route as if real).
   Dispatcher's call: they read the destination off the later arrival.
3. **"Finish live unloading at pactra #3 move to Dock 47" became a leg to
   UNKNOWN.** A door read as travel. Prompt now states a door is never a
   destination (verified against the live parser); CASE 3 resolves each door to
   its building via `docks.csv` and stamps the completion on the trip that
   ended there -- and only if it ended *there*, or the unload lands on the
   wrong leg.
4. **`replay_scratch` now says where it is** at the end of a run. It was always
   kept (dropped only at the start of the next run); nothing was deleting it.

New: `data/docks.csv` + `location_docks` table + `ai_engine.facility_for_dock`
/ `dock_use`. `dock_use` is recorded and **not yet acted on** -- it is what
would later let load type be read off the door rather than guessed.

Replay 08/28 went 86/120 → 88/120 matched (72%→73%). That number only compares
origin, destination and *departure* time, so it does not see the arrival times,
DO numbers and trailers these fixes corrected.

## Done 2026-08-30 (later, uncommitted)

Two cases the dispatcher reported from 08/28, both traced to the same shape of
defect: a signal that was already in the message went unread.

1. **The paperwork says where the load is going.** "Load trailer pickup sds
   dock28 #77209" captioned a BOL consigned to 200 Momeni Lane. The vision pass
   never read SHIP TO at all, so the run was lost. Vision now extracts
   `ship_to_address`, `ai_engine.facility_for_address` resolves it against the
   `address` column of `location_codes` (house number + street only -- the
   suffix drifts between the BOL's print and locations.csv), and it fills the
   destination **only** when the driver named none. Skipped for a duplicate
   BOL, and skipped when the consignee is the site they are standing on.
   Falls back to the existing card when it cannot resolve.
2. **That message reached no handler at all.** The parser files it
   `CASE_2_DESTINATION_ARRIVAL` with SDS as the *destination* -- "pickup sds
   dock28" reads as travel TO sds. With a trip open to SDS the arrival branch
   stamped the arrival and returned clean, and the hook was never seen; with no
   open trip, the orphan-pickup card tested `origin_loc` only, which was
   UNKNOWN. Both now route through `start_hooked_load`.
3. **A delivered load left the yard booked LOADED.** "Finish live unloading at
   pactra #10 heading to sds" with a receiver-stamped BOL. The branch meant to
   catch this tested `action_type` for `UNLOAD_COMPLETED`/`FINISHED_UNLOAD`,
   which **the parser cannot emit** -- its vocabulary is `LIVE_UNLOAD` /
   `DROP_DOCK` / `DROP_YARD` / `DROP_DOOR` / `BOBTAIL_ARRIVE`. It never fired,
   so load status fell through to inheriting the previous leg's. Replaced with
   `just_delivered` (receiver stamp, or work_finished on an unload) and its
   mirror `just_loaded` -- the `LIVE_LOAD`/`HOOK` branch was equally dead, so
   "live loading finished load 200 to E2F" was departing EMPTY.
4. **Receivers stamp now, they do not sign.** The vision prompt explicitly said
   a company stamp is NOT a receiver signature, so every stamped POD read as
   missing. It now turns on WHICH BLOCK the mark sits in, not on handwriting.
5. **`do_number` was capturing the printed "Do No." field** -- the shipper's
   own reference, which looks like the BOL number -- instead of the SDS clerk's
   hand-written yard slot. Prompt now requires handwriting and digits only.
6. `compress_image` raised on any RGBA PNG ("cannot write mode RGBA as JPEG")
   and silently sent the full-size original. Screenshots are RGBA.

`CASE 1`'s departure INSERT is now `open_departure_leg`, shared with the hooked
-load paths rather than copied.

**Verified against the two real photos** (`extract_bol_locally` on the
dispatcher's screenshots): ship-to resolves to 200F on both, the stamp reads as
`receiver_signed`, and `do_number` is `33` on one and null on the other.

Not yet checked: whether the CASE 1 **auto-heal** swallows a POD posted
alongside an onward departure. It claims any open LOADED leg missing a BOL, and
would then never reach the departure. It did not fire on 08/28 because the
inbound leg already had its paperwork.

## On first deploy, expect

POD alerts, parse-failure cards and dwell alerts fire **for the first time
ever** — a burst reflecting accumulated habit, not a regression. Drivers will
start getting clock-in acknowledgements and an occasional gate-report nudge
(max once a week each). Tell them before it starts talking. Check `/roster` on
day one: anyone unrecognised is being silently ignored.
